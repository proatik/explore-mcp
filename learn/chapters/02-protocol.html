💡 Learn

Only three shapes

Every MCP message is one of these. The highlighted fields decide which.

Request asks for work

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "get_stock_level",
    "arguments": { "productId": 101 },
    "_meta": { … }
  }
}
  • id is a string or integer, never null (stricter than plain JSON-RPC)
  • An id can't be reused while that request is still waiting
  • Sent by the client to start an operation

Response answers it

{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "content": [{ "type": "text",
      "text": "14 in stock" }]
  }
}
  • Same id as the request it answers
  • Either result or error, never both
  • Results carry resultType; a missing one means "complete"

Notification just tells

{
  "jsonrpc": "2.0",
  "method": "notifications/
    resources/updated",
  "params": {
    "uri": "shop://products/101"
  }
}
  • No id, and the receiver must not reply
  • Can flow either way: progress, updates, cancellation
  • Method names start with notifications/

Method names you'll see

A noun, a slash, a verb. Tap one to see what it does.

Every request stands alone

In 2026-07-28 the protocol is stateless. Each request brings its own context in _meta.

🧾 What's inside _meta

"_meta": {
  "io.modelcontextprotocol/protocolVersion": "2026-07-28",
  "io.modelcontextprotocol/clientCapabilities": {},
  "io.modelcontextprotocol/clientInfo": {
    "name": "shop-assistant",
    "version": "1.0.0"
  }
}

Highlighted keys are required on every request. clientInfo is optional but recommended.

📏 The rules

  • The server must not rely on earlier requests for version, capabilities or identity
  • A missing required field → error -32602, and HTTP 400
  • Long-lived work (like a subscription) is referenced by an explicit id
  • clientInfo and serverInfo are self-reported: fine for logs, not for security
  • Legacy (2025-era) clients open a session with initialize. A dual-era server serves both (Chapter 01)

🔑 Cursor rules

          
    
            
  • Supported by tools/list, resources/list, resources/templates/list, prompts/list
    • 
            
  • The server picks the page size. Never assume one
    • 
            
  • A cursor is opaque: don't parse, edit or build it
    • 
            
  • No nextCursor means the end. An empty string is still a valid cursor
    • 
            
  • A bad cursor should get error -32602
    •

Two very different failures

      
A broken request gets a JSON-RPC error. A valid call that can't succeed gets a result with isError: true. Pick a situation.

Error codes worth knowing

      
Standard JSON-RPC codes for protocol failures, plus three codes MCP defines itself.

      

        
-32700Parse error: not valid JSON

        
-32600Invalid Request: not a valid request object

        
-32601Method not found

        
-32602Invalid params: unknown tool, bad cursor, missing _meta

        
-32603Internal error on the receiver

        
-32020HeaderMismatch (MCP)

        
-32021MissingRequiredClientCapability (MCP)

        
-32022UnsupportedProtocolVersion (MCP)

      

      
Error codes must be integers. -32002 (old "resource not found") is retired in 2026-07-28 and replaced by -32602; clients should still accept it from older servers.

🎯 Key takeaways

        
    
          
  • Every message is a request (has an id), a response (same id, result or error) or a notification (no id, no reply).
    • 
          
  • Broken requests get a JSON-RPC error. Failed operations get a result with isError: true the model can act on.
    • 
          
  • In 2026-07-28 every request is self-contained: _meta carries the version and capabilities.
