🛠️ Tool call

Tool error · isError: true 
{ "isError": true,
  "structuredContent": { "error": {
    "code": "FORBIDDEN",
    "details": { "requiredScope": "inventory:write" } } } }

The model reads it and can tell the user why. Nothing ran. FORBIDDEN is an example code your own server might define.

📚 Resource read

Protocol error 
{ "error": {
  "code": -32600,
  "message": "Forbidden: reading shop://orders/5004 requires the \"orders:read\" scope." } }

A failed read has no result to show, so a JSON-RPC error fits.

🌐 OAuth

Production: OAuth 2.1

What the 2026-07-28 spec defines for HTTP servers. A static dev token covers only step 8. An authorization server adds steps 1 to 7.

🎯 Audience binding

  • Client sends resource= its server's URI (RFC 8707).
  • Server MUST reject tokens issued for anyone else.

🚫 No token passthrough

  • Server MUST NOT forward the client's token upstream.
  • Prevents the "confused deputy": a server acting with powers nobody gave it.

📮 Header only

  • Authorization: Bearer … on every request.
  • Never in the URL query string.

A simple dev setup vs production

Keep token checking behind one verifier. Swap static tokens for OAuth later, keep everything else.

▶ Try it for real

Against an MCP server you build. https://store.example.com/mcp is a placeholder for your own endpoint. The Inspector needs Node 22.19 or newer.

1 · KNOCK WITHOUT A TOKEN
curl -i -X POST \
  https://store.example.com/mcp \
  -H "Content-Type: application/json" \
  -d "{}"

Expect 401 with a WWW-Authenticate: Bearer challenge. With OAuth it carries resource_metadata.

2 · READ THE METADATA
curl \
  https://store.example.com/.well-known/oauth-protected-resource

Or the URL from resource_metadata. Look for authorization_servers and scopes_supported.

3 · CONNECT WITH A TOKEN
npx @modelcontextprotocol/inspector \
  --server-url https://store.example.com/mcp \
  --transport http --protocol-era auto \
  --header "Authorization: Bearer <read-only token>"
4 · TRY A WRITE AS READ-ONLY
npx @modelcontextprotocol/inspector --cli \
  https://store.example.com/mcp --transport http --protocol-era auto \
  --header "Authorization: Bearer <read-only token>" \
  --method tools/call --tool-name update_stock \
  --tool-arg productId=102 --tool-arg operation=increment \
  --tool-arg quantity=1 --tool-arg reason=Recount

Expect a refusal: 403 insufficient_scope with OAuth, or a scope tool error in a simple setup. Nothing should change.

🎯 Key takeaways

  • Authentication (who) happens at the HTTP door. Authorization (what) happens at every tool, resource and prompt.
  • Give each client the least scope it needs. A read-only agent gets read scopes only.
  • Keep credentials apart: never pass the client's token upstream. In production, use OAuth 2.1 with audience-bound tokens.
