💡 Learn

Progress: an opt-in heartbeat

The client asks for progress with a token. The server may then report against that token. Tap a highlighted field.

① Client request

A normal tool call, plus a token in _meta.

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "get_stock_level",
    "arguments": { "threshold": 5 },
    "_meta": { "progressToken": "scan-7" }
  }
}

② Server notification

Sent as many times as the server likes, then the normal result.

{
  "jsonrpc": "2.0",
  "method": "notifications/progress",
  "params": {
    "progressToken": "scan-7",
    "progress": 3,
    "total": 12,
    "message": "Scanned 150 products"
  }
}
🙋
Client opts inNo token, no progress. The server may still choose to send none.
📈
Always increasesprogress must go up every time, even when the total is unknown.
❔
Total is optionalOmit it when you can't know the size up front. Values may be decimals.
🏁
Stops at the endNo progress after the result. Both sides should rate-limit to avoid floods.

Source: MCP specification, revision 2026-07-28, "Progress".

💡 Learn

Cancellation: stop wasted work

How the client says "never mind" depends on the transport. Either way, expect races.

How the client cancels

The race

    The spec requires both sides to handle these races gracefully.

    🧹 What each side should do

    • Server: stop processing, free resources, and send no response.
    • Server: may ignore it if the request is unknown, already done, or can't be cancelled.
    • Client: ignore any response that arrives after cancelling.
    • Both: log the reason. The UI should show that a cancel was requested.

    ⏱️ Timeouts are cancellation too

    • Set a timeout on every request you send.
    • When it fires, cancel the request and stop waiting.
    • You may reset the clock on each progress update…
    • …but always keep a maximum, in case progress never ends.

    Source: MCP specification, revision 2026-07-28, "Cancellation".

    Retries without double writes

    The network drops the reply to a stock change. Did it happen? Retry with and without an idempotency key.

    What happened

    🔑 A pattern, not protocolIdempotency keys are a general distributed-systems practice. In this example the tool accepts an optional idempotencyKey argument.
    📖 Reads retry, writes don'tA careful server retries its own upstream reads with backoff. Writes run once, because a timed-out write may have landed.
    🏷️ Hints help the clientupdate_stock declares idempotentHint: false, so a careful client won't blindly retry it.

    🎯 Key takeaways

    • Long calls should talk: send progress whenever the client asks for it.
    • Cancel cleanly: stop the work, free resources, and expect races.
    • Retry writes only with an idempotency key, or don't retry them at all.
