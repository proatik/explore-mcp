Capabilities: use only what was declared

  • The server lists its capabilities in server/discover (or the legacy initialize result).
  • A modern client sends its own capabilities with every request, in _meta.
  • Never call a feature the other side didn't declare. A well-built client only lists tools, resources and prompts the server advertised.
  • Optional extensions are negotiated under capabilities.extensions. If only one side supports one, it falls back to core behavior or rejects the request.

    Why the server can stay simple

    • A stateless server can build a fresh MCP server object for each HTTP request. Nothing protocol-related is kept between requests.
    • So you can run several instances behind a load balancer, with no session affinity.
    • Long-lived state (the store's API client, an idempotency store) is created once at start-up, outside the protocol.

    What happens next?

    Six real situations. Predict the outcome.

    ▶ Try it for real

    Use the official MCP Inspector. Needs Node 22.19+.

    1. Connect to the public example server over Streamable HTTP. It is protected with OAuth, so expect a 401 challenge first; follow the Inspector's auth flow to sign in (Chapter 10 explains every step).
      npx @modelcontextprotocol/inspector --server-url https://example-server.modelcontextprotocol.io/mcp --transport http --protocol-era auto
    2. Watch the era change. The Inspector defaults to legacy (plain initialize); auto probes server/discover first and falls back. Connect once as modern, once as legacy, and compare the messages.
      ... --protocol-era modern
... --protocol-era legacy
    3. Run a local server over stdio instead. Same messages, different transport.
      npx -y @modelcontextprotocol/inspector npx @modelcontextprotocol/server-everything
    4. Point it at a server you built, with its token.
      npx @modelcontextprotocol/inspector --server-url http://localhost:3000/mcp --transport http --protocol-era auto --header "Authorization: Bearer <token>"
    5. Break it on purpose: send a wrong token. A good client reports the auth failure at once, with no retries.

    🎯 Key takeaways

    • Revision 2026-07-28 is stateless: every request carries its version, identity and capabilities.
    • stdio for a local subprocess, Streamable HTTP for a remote server. Same JSON-RPC messages.
    • Retry only what's safe: transient failures yes, auth never, writes reported instead of repeated.
